# LetsBeParents — мобильное приложение (React Native / Expo)

Это настоящее React Native приложение, которое ходит **в тот же самый бэкенд**,
что и сайт (`lbp/backend`, FastAPI + Postgres) — не отдельная копия и не
макет. Один аккаунт, одни лайки, одни чаты что на сайте, что в приложении,
потому что оба обращаются к одному и тому же API.

## Что уже готово

- Вход и регистрация (`/api/auth/login`, `/api/auth/signup`) — по-настоящему,
  с реальными ошибками с сервера (неверный пароль, email уже занят и т.д.)
- Вход через Google и Apple (`/api/auth/firebase`) — тот же Firebase-проект,
  что уже используется на сайте. **Нужна твоя настройка перед первым
  запуском** — см. "Про вход через Google/Apple" ниже, это самое важное,
  что нужно сделать вручную во всём приложении. **Но даже после этой
  настройки вход (и через соцсети, и обычный, по email/паролю) не заработает
  без ОДНОГО серверного изменения, которое я думала, что уже сделано, а
  оказалось — нет** — см. "Одно изменение в бэкенде" ниже, это блокер для
  входа в приложение целиком, не мелочь
- Каталог/Browse (`/api/member/catalog`) — список анкет, лайк/анлайк
- Профиль анкеты (`/api/member/catalog/{id}`) + кнопки "Пожаловаться" и
  "Заблокировать"
- Лайки (`/api/member/likes`) — 4 вкладки, как на сайте: "Лайкнули вас"
  (Premium), "Совпадения", "Мои лайки", "Посетители" (кто смотрел ваш
  профиль, тоже Premium, `/api/member/profile-views`). Экран был переписан
  заново — см. ниже про найденный баг
- Сообщения — список диалогов (`/api/member/conversations`) и сам чат
  (`/api/member/conversations/{id}/messages`, отправка сообщений)
- Мой профиль — базовая информация + выход из аккаунта, кнопка "Настройки"
- Настройки (`/api/member/settings`) — видимость в каталоге, уведомления
- Фото профиля (`/api/member/photos`) — загрузка, удаление, до 6 штук
- Верификация (Didit) — статус + запуск веб-проверки во встроенном браузере
- Подписка/Premium — статус, запрос Monthly/Annual (Quarterly временно
  недоступен — см. комментарий в `src/api/subscription.ts`, это ограничение
  самого бэкенда, а не приложения)
- Заблокированные пользователи — список + разблокировка
- Жалоба на анкету — выбор причины, отправка на сервер
- Каталог клиник и юристов (`/api/public/clinics`, `/api/public/lawyers`) —
  поиск, карточка с контактами, отдельная вкладка "Clinics & Lawyers"
- Избранное/"Сохранённые" (`/api/member/favourites`) — сердечко на карточке
  клиники/юриста, отдельный экран со всеми сохранёнными
- Аудио- и видеозвонки (LiveKit) — входящий вызов, приём/отклонение, экран
  активного звонка. **Важная оговорка ниже** — эта часть не заработает в
  обычном Expo Go, нужна отдельная сборка (см. "Про звонки" ниже)
- Перевод интерфейса — English / Русский / Español, те же 3 языка, что и на
  сайте (см. "Про перевод интерфейса" ниже)
- Ресурсы и инструменты — те же гайды/чек-листы/шаблоны (.docx), что и на
  сайте, плюс тест на совместимость co-parenting (26 вопросов, без баллов и
  вердикта). Открывается из вкладки "Профиль" → "Resources & Tools". См.
  "Про раздел Ресурсы и инструменты" ниже
- Иконка приложения и splash screen — настоящий фирменный знак с сайта
  (не заглушка), на брендовом градиенте. См. "Про иконку и splash screen"
  ниже — это снимает один из пунктов, которые раньше блокировали публикацию
  в TestFlight

## Про вход через Google/Apple

Я сначала ошибочно сказала, что раз в приложении нет входа через соцсети —
то и делать с этим ничего не нужно. Это было неточно: на **сайте** вход
через Google и Apple уже есть и реально работает (кнопки "Continue with
Google"/"Continue with Apple" на странице входа/регистрации,
`lbp/frontend/src/firebase-auth.ts`) — в **приложении** его просто никогда
не строили. Теперь построила, тем же способом, что и сайт: тот же Firebase-
проект, тот же эндпоинт `/api/auth/firebase` на бэкенде — так что аккаунт,
созданный через Google в приложении, это тот же аккаунт, что и через Google
на сайте.

**Это единственное место во всём приложении, где без твоих действий оно
работать не будет** — не из-за кода, а потому что вход через Google/Apple
физически не может заработать без ключей от твоего Firebase-проекта. Нужно:

1. Зайти на console.firebase.google.com в тот же проект, которым пользуется
   сайт. Настройки проекта (шестерёнка) → General → "Your apps" → там уже
   должно быть Web-приложение (сайт им пользуется) — открой его "SDK setup
   and configuration" и скопируй все 6 значений (apiKey, authDomain,
   projectId, storageBucket, messagingSenderId, appId) в `.env` этого
   мобильного проекта (места для них уже подготовлены в `.env.example`,
   с пояснениями). Эти значения одинаковые для всего проекта — не секретные
   пароли, просто адрес, куда стучится приложение.
2. В том же Firebase-проекте (это одновременно и Google Cloud проект) →
   console.cloud.google.com → APIs & Services → Credentials — там уже есть
   "Web client (auto created by Google Service)", как только в Firebase
   включён вход через Google. Его Client ID тоже в `.env` (переменная
   `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`) — этого достаточно для проверки в
   Expo Go. Для настоящей сборки под iOS/Android там же нужно будет создать
   ещё iOS/Android Client ID — подробности в `.env.example`.
3. Для Apple — доп. настройка Firebase, скорее всего, уже сделана (раз на
   сайте кнопка "Continue with Apple" уже работает). Со стороны приложения
   нужно только в Apple Developer (developer.apple.com) на App ID
   `com.letsBeParents.letsBeParents` включить галочку "Sign In with Apple" —
   это можно сделать и позже, вручную, или через EAS Build, если он сам
   будет управлять сертификатами.

   `com.letsBeParents.letsBeParents` — это подтверждённый реальный
   идентификатор, уже зарегистрированный и в Google Cloud Console, и в
   Apple Developer (не мой вариант `com.letsbeparents.app`, который был
   тут раньше, — его я поменяла на настоящий). Он же прописан в
   `app.json` (`ios.bundleIdentifier` и `android.package`) — важно, чтобы
   везде было ровно одно и то же значение, иначе Google/Apple будут
   отклонять вход.

**Насчёт "приложение не запустится без Firebase":** раньше тут было
написано, что без пункта 1 приложение вообще не стартует. Это неверно —
уже проверено на реальном запуске: с пустыми `EXPO_PUBLIC_FIREBASE_*` в
`.env` приложение прекрасно доходит до экрана входа, просто кнопки
"Continue with Google/Apple" будут неактивны (`useAuthRequest()` возвращает
`request: null`, когда client ID не задан — см. `SocialAuthButtons.tsx`).
Так что пункт 1 нужен только для того, чтобы РАБОТАЛ вход через
Google/Apple, а не для запуска приложения вообще.

**Честно говоря:** это единственная часть приложения, где мне не хватило
не просто "не смогла запустить", а "не смогла свериться с документацией" —
у пакета `expo-auth-session` (библиотека, которая открывает окно входа
Google) API менялся между версиями, и я не смогла проверить в интернете,
какая именно форма сейчас актуальна. Написала по наиболее распространённому
паттерну, но при первом реальном запуске именно тут вероятнее всего
понадобится сверка с актуальной документацией `expo-auth-session` (это
задача для программиста, не для тебя). Часть с Apple (`expo-apple-
authentication`) — гораздо более простой и стабильный API, там таких сомнений
нет. Кнопка Google сейчас — просто текст "Continue with Google"; у Google
есть свои правила по оформлению этой кнопки (логотип "G" и т.д.) — стоит
подставить их официальную иконку перед реальным релизом, я оставила
текстовую заглушку.

## Что ещё НЕ сделано (следующие шаги)

Больше готовых разделов из того, что реально есть на сайте, на сегодня не
осталось — избранное клиник/юристов, звонки, перевод интерфейса, ресурсы/тест
на совместимость и теперь вход через Google/Apple — всё есть в приложении.
Из мелкого: раздел Resources & Tools пока открыт из "Профиль", а не из
отдельной вкладки внизу — так сделано специально, чтобы не переполнять
нижнюю навигацию (на сайте это тоже не отдельный первичный раздел, а ссылка
в шапке/подвале).

**Важно:** весь код в этой папке написан вручную и проверен построчно, но
ни разу не был по-настоящему собран и запущен (`npm install` /
`npx expo start`) — ни у меня, ни на этом компьютере нет доступа к npm.
Первым делом после установки пакетов возможны мелкие ошибки типов/имён,
которые обычно решаются за минуты, но их нужно поймать локально у
программиста.

**Отдельный проход по коду (без сборки, просто перечитала всё построчно)**
нашёл и починила 4 настоящих бага в уже написанном коде — до того, как
программист успел их найти сам: (1) экран верификации не передавал язык
интерфейса в Didit, всегда открывал проверку на английском; (2) карточка
клиники/юриста, открытая из "Избранного" или из каталога, всегда
показывала "🤍 Save" вместо "❤️ Saved", даже если она уже сохранена — при
следующем нажатии это могло вызвать не тот запрос (лайк вместо анлайка); (3)
в чате при неудачной отправке сообщения текст возвращался в поле ввода, даже
если человек уже успел написать что-то новое — новый текст стирался; (4) в
каталоге клиник/юристов быстрое переключение вкладки Clinics/Lawyers во
время ещё не завершившегося поиска могло показать чужие (устаревшие)
результаты не в той вкладке. Все четыре — гонки состояний/пропущенные
параметры, а не что-то серьёзное, но приятно, что нашлись не в самом конце.

**Отдельно, уже потом, нашёлся баг посерьёзнее** — экран "Лайки" был написан
до того, как я до конца сверила реальный ответ `/api/member/likes` с
`main.py` (это было честно помечено в комментарии в коде: "shape not fully
verified"). Оказалось, что бэкенд вообще не возвращает плоский список — он
отдаёт `{ likesYou, likesYouCount, likesYouLocked, myLikes, matches,
readThroughId }`, а старый код приложения читал несуществующее поле
`items`. То есть экран "Лайки" всегда показывал бы пустой список, что бы ни
было в базе. Переписала экран под реальный формат (заодно добавила вкладку
"Посетители" — её вообще не было) — теперь показывает то же самое, что и на
сайте.

## Одно изменение в бэкенде (нужно, но НЕ сделано — см. проверку ниже)

Сайт входит в аккаунт через "невидимую" HttpOnly cookie, которую не может
прочитать мобильное приложение. Поэтому приложению *нужно*, чтобы
`lbp/backend/main.py` в ответах `/api/auth/login`, `/api/auth/signup` и
`/api/auth/firebase` добавил новое поле `"sessionToken"` — при этом всё, что
было (включая cookie для сайта), продолжало бы работать как раньше. Приложение
уже написано в расчёте на это поле: сохраняет его на телефоне
(`src/context/AuthContext.tsx`) и отправляет на каждый запрос как
`Authorization: Bearer <token>` (`src/api/client.ts`).

**ПРОВЕРЕНО и это НЕ так — на момент этого код-ревью изменение в бэкенд не
попало.** Я сверила это утверждение с реальным `lbp/backend/main.py`
(10 027 строк, есть в песочнице) построчно: ни слова "sessionToken", ни
комментариев "native/mobile clients" там нет вообще — `return` у всех трёх
эндпоинтов (`auth_login`, `auth_signup`, `auth_firebase`) отдаёт только
`expiresAt`/`user` (+ `provider`/`isNewUser` у firebase-эндпоинта), токен
нигде наружу не отдаётся, только кладётся в HttpOnly cookie
(`set_user_session_cookie`). Более ранняя версия этого README утверждала
обратное ("уже сделано") — это было неверно, прошу прощения за путаницу.

**Практическое следствие: пока это не исправлено на бэкенде, вход в
приложении не работает вообще — ни обычный (email/пароль), ни новый через
Google/Apple.** Firebase-логин технически пройдёт успешно (`signInWithCredential`
сработает, `POST /api/auth/firebase` на бэкенде тоже отработает и создаст
сессию), но приложение получит `res.sessionToken === undefined`, сохранит
это как токен и все следующие запросы будут уходить с
`Authorization: Bearer undefined` → 401, то есть человек как будто "не
залогинен", хотя сессия на сервере создалась. Это не баг именно
Google/Apple-кнопок — та же проблема уже была у обычного входа по паролю
(`login`/`signup`), просто вход через соцсети её унаследовал.

**Что нужно программистам бэкенда:** добавить поле `"sessionToken"` (сырое
значение `token` из `create_session()`) в JSON-ответ всех трёх эндпоинтов —
это единственное реальное серверное изменение, без которого мобильное
приложение (весь вход целиком, не только соцсети) не может авторизовываться.

Отдельно нашла (но не стала тихо чинить) ещё один похожий разнобой между
сайтом и бэкендом: сайт при аудиозвонке отправляет `callType: "AUDIO"`, а
бэкенд (`CallCreatePayload` в main.py) принимает только `"VOICE"` или
`"VIDEO"` — то есть аудиозвонок с сайта, скорее всего, у него сейчас не
проходит валидацию и падает с ошибкой 422. Мобильное приложение отправляет
`"VOICE"`, как хочет бэкенд, так что в приложении это работает — но
программистам стоит показать это место на сайте.

## Про звонки (LiveKit) — нужна отдельная сборка, не Expo Go

Всё остальное в приложении открывается в обычном приложении **Expo Go** —
удобно для быстрой проверки. Звонки — исключение: `@livekit/react-native`
подключает настоящий нативный код (WebRTC), которого в Expo Go просто нет.
Чтобы протестировать звонки, после установки пакетов (см. ниже) нужно:

```
npx expo prebuild
```

а дальше собрать и запустить обычное разработческое приложение — либо через
`eas build --profile development` (если настроен EAS), либо открыть папки
`ios/`/`android/`, которые появятся после `expo prebuild`, в Xcode /
Android Studio и запустить оттуда на телефоне или симуляторе. Это ровно то,
что в любом случае понадобится перед публикацией в App Store / Google
Play — Expo Go никогда не используется для финальной сборки, так что это
не лишний шаг, а следующий естественный.

**Обновление после первого реального запуска:** утверждение выше ("всё
остальное открывается в Expo Go") оказалось не совсем точным — приложение
реально зависало намертво прямо на splash screen при первом запуске в Expo
Go, без единой ошибки в логе. Причина: `App.tsx` вызывал
`registerGlobals()` из `@livekit/react-native` безусловно, при любом
запуске — а эта функция обращается к нативному WebRTC-модулю, которого в
Expo Go нет. Дальше выяснилось, что дело не только в самом вызове: `import
{ registerGlobals } from "@livekit/react-native"` (и такие же импорты в
`CallOverlay.tsx` и `CallContext.tsx`) выполняются в момент загрузки файла,
ещё до всех проверок — так что даже обёртка "не вызывать в Expo Go" не
спасала, крашилось на самой загрузке модуля с ошибкой "WebRTC native module
not found".

Починено так: `App.tsx`, `CallContext.tsx` и (через `App.tsx`)
`CallOverlay.tsx` теперь используют `require(...)` внутри `if
(!isExpoGo)` вместо обычного `import` — модуль LiveKit/WebRTC в Expo Go
вообще не загружается, а не просто "не вызывается". Определяется Expo Go
через `expo-constants`: `Constants.executionEnvironment ===
ExecutionEnvironment.StoreClient`. В самом Expo Go экран звонка теперь
просто сразу пишет "не удалось подключиться" вместо зависания — это
ожидаемо, для реальных звонков всё равно нужна отдельная сборка (см. выше).

**Честно говоря:** код звонков (`src/context/CallContext.tsx`,
`src/screens/CallOverlay.tsx`) я написала по памяти о документации LiveKit
для React Native (у меня нет доступа в интернет, чтобы свериться с ней
прямо сейчас), и не смогла ни разу собрать и запустить само приложение (см.
ниже про npm) — так что эту часть не проверяла даже приблизительно. Отдельно
не уверена на 100% в `app.json` → `plugins`: сейчас там только
`@config-plugins/react-native-webrtc`, но у самого `@livekit/react-native`,
возможно, есть свой конфиг-плагин с отдельным именем — перед `expo prebuild`
стоит свериться с актуальной страницей "Expo" в документации LiveKit
(docs.livekit.io → React Native → Expo) и добавить его в этот список, если
он там есть. Остальной код (экраны, работа с API) на том же уровне
уверенности, что и раньше.

## Про перевод интерфейса

Приложение говорит на трёх языках — English / Русский / Español, ровно те же
языки, что поддерживает сайт (см. `CookieLocale` в `lbp/frontend/src/ui.tsx`).
Все тексты интерфейса лежат в одном файле `src/i18n/translations.ts` (по
одному словарю ключ→строка на каждый язык, ~185 ключей), а `src/i18n/I18nContext.tsx`
даёт каждому экрану функцию `t("some.key")` вместо текста, зашитого в код.

Важная деталь: язык интерфейса — это то же самое поле `interfaceLanguage`,
которое сайт уже хранит через `/api/member/settings`. Поэтому:

- при входе в аккаунт приложение читает текущий `interfaceLanguage` с сервера
  и сразу открывается на нужном языке — если человек в браузере на сайте
  переключился на русский, в приложении тоже будет русский;
- в самом приложении (Настройки → Language) можно переключить язык —
  это меняет и то, что видно в приложении прямо сейчас, и сохраняется на
  сервере, так что и сайт при следующем открытии тоже будет на этом языке.

Ничего в бэкенде для этого менять не пришлось — `interfaceLanguage` там уже
был.

**Как обычно:** файл с переводами написан и сверен вручную (проверила, что
во всех трёх словарях ровно одинаковый набор ключей, без пропусков и лишних),
но само приложение с этими текстами ни разу не запускалось (см. оговорку
выше про `npm`). Если что-то из английского текста вдруг проскочило
непереведённым на каком-то экране — это самое вероятное место, куда
программисту стоит заглянуть в первую очередь.

## Про раздел "Ресурсы и инструменты"

Это то же самое, что на сайте есть под `/resources` — чек-листы, шаблоны и
компатибилити-тест для co-parenting, донорства и планирования. В приложении
открывается из вкладки "Профиль" → "Resources & Tools".

Важная техническая деталь: это единственный раздел бэкенда, который на самом
деле не про бэкенд — весь список гайдов и все 26 вопросов теста лежат прямо
в коде сайта (`RESOURCES_CATEGORIES` / `QUIZ_QUESTIONS` в `ui.tsx`), а не в
базе данных, и у бэкенда нет для этого API вообще. Я скопировала эти же
данные в `src/data/resources.ts` дословно — так что если на сайте
что-то поменяют в текстах гайдов или вопросах теста, в приложении это само
собой не обновится, нужно будет вручную скопировать изменения в этот файл.

Сами .docx-файлы (шаблоны для скачивания) физически лежат не в бэкенде, а в
статике сайта (`/web-static/resources/*.docx`). Программист **подтвердил**
(раньше это было только моей догадкой по коду сайта — теперь факт): сайт и
бэкенд в проде действительно на одном домене, отдельного поддомена `api.*`
нет, Nginx сам перенаправляет `/api` на бэкенд — см. `.env.example`. Значит
и файлы шаблонов должны быть доступны по тому же адресу, что и API. Поэтому
в приложении файлы скачиваются с `EXPO_PUBLIC_API_BASE_URL` + путь; если
вдруг у программистов сайт и API всё же на разных доменах, есть отдельная
переменная `EXPO_PUBLIC_SITE_BASE_URL` в `.env.example` — под неё можно
подставить настоящий адрес сайта.

Тест на совместимость — как и на сайте, целиком локальный: ничего не
отправляется на сервер, результат никак не привязан к аккаунту. "Скачать
результаты" на сайте — это файл в браузер; в приложении это открывает
системное меню "Поделиться" (можно сохранить в Файлы, отправить в мессенджер
и т.д.) — кнопки "Печать" отдельно нет, но на iPhone в этом же меню
"Поделиться" есть встроенная опция печати, так что по сути ничего не
потеряно.

Раздел специально оставлен только на английском, как и на сайте — там это
тоже пока не переведено ни на русский, ни на испанский (в отличие от всего
остального интерфейса приложения, который уже говорит на трёх языках, см.
"Про перевод интерфейса" выше). Как только на сайте появится перевод этого
раздела — его нужно будет перенести и сюда.

**Как обычно:** содержимое (гайды, вопросы теста) — это не мой текст, а
дословная копия того, что уже есть и одобрено на сайте, так что тут ничего
придумывать не пришлось. А вот сами экраны (как это показано на телефоне) —
новый код, ни разу не запускался, тот же уровень уверенности, что и везде.

это буквально один и тот же файл-первоисточник, а не что-то похожее, но
нарисованное заново.

Три файла лежат в `assets/`:

  на белом фоне)
- `splash.png` (1242×1242, белый фон, значок по центру) — экран загрузки,
  который на секунду показывается при открытии приложения

**Важная оговорка, как и со всем остальным в этой папке:** я не смогла
собрать настоящий нативный билд (`expo prebuild`), чтобы своими глазами
увидеть, как иконка выглядит на реальном телефоне/симуляторе — ни здесь,

занимает часть холста с запасом на обрезку), но именно на реальном
Android-лаунчере это стоит перепроверить глазами при первой сборке.

Если у команды есть отдельный, более новый логотип специально для
иконки приложения (не веб-favicon) — можно будет просто заменить эти три
PNG-файла в `assets/`, ничего больше менять не придётся.

## Приведение дизайна к настоящему прототипу (в процессе, батч 1 из N)

После того как приложение впервые реально заработало на телефоне, пришёл
однозначный фидбек: экраны не похожи на согласованный HTML-прототип
(`Claude outputs/app-prototype-inline.html` в твоей папке LBP2, плюс
мокапы `mockups*.png` там же). Открыла и разобрала этот файл — там
настоящая, гораздо более цельная дизайн-система: розовый `#f31260` как
основной цвет (а не фиолетовый, который был в `theme.ts` раньше — это
была ошибка, ссылка на устаревший `style.css.txt`), круглые pill-кнопки,
светло-серые поля ввода, отдельный экран Welcome, и Browse — это
карточки в стиле Tinder (свайп пальцем), а не список.

**Важное открытие по ходу дела:** прототип описывает более широкий,
будущий редизайн продукта — там есть разделы Family, Plan & Documents,
Knowledge Hub, которых просто нет в реальном бэкенде (проверила по
`backend/main.py` — таких эндпоинтов не существует вообще). Это
подтверждает более раннюю пометку в коде `MainTabs.tsx` про то, что
приложение специально следует настоящей структуре сайта (Catalog / Likes
/ Messages / Directory / Resources / Me), а не этому более амбициозному
редизайну. Поэтому я НЕ стала строить красивые, но полностью бутафорские
экраны без данных за ними — если команда решит добавить эти разделы на
бэкенде, тогда есть смысл строить и мобильные экраны под них.

**Что сделано в этом батче:**
- `src/theme.ts` — новая палитра (розовый/синий вместо фиолетового/синего),
  подтянута на ~60 мест по всему приложению одним файлом (кнопки, активная
  вкладка, спиннеры, ссылки)
- Новый экран **Welcome** (`WelcomeScreen.tsx`) — первый экран при запуске
  не залогиненным; градиентный фон вместо видео из прототипа (видео-ассет
  пока не передан)
- **Login/Signup** переписаны под точную вёрстку прототипа (`auth-page` в
  их CSS): логотип по центру, крупный заголовок, поля на светло-сером
  фоне, розовая pill-кнопка, глазок показать/скрыть пароль внутри поля
- Новый экран **Forgot Password** (упрощённо: только email → реальный
  `POST /api/auth/forgot-password`, без экрана с 6-значным кодом из
  прототипа — это отдельный, более крупный кусок работы)
- **Browse (`CatalogScreen.tsx`) переписан с нуля** — теперь это
  свайпаемые карточки в стиле Tinder, как в прототипе и как ты выбрала:
  фото на весь экран, бейдж типа профиля, "Ищет: …" из настоящего поля
  `lookingFor`, кнопки Х (пропустить) / 👤 (открыть профиль) / 💬
  (написать, через настоящий `POST /api/member/conversations`) / 👍
  (лайкнуть, через настоящий `POST /api/member/likes/:id`). Свайп вправо
  = лайк, влево = пропустить. У бэкенда нет отдельного "пропустить" —
  это чисто локальное действие, профиль может снова появиться после
  полной перезагрузки ленты
- **Me (профиль)** — переоформлен под карточку-список с аватаром сверху,
  как в прототипе

**Технический риск, на который стоит обратить внимание (ОБНАРУЖЕН И
ИСПРАВЛЕН на практике, сентябрь 2026):** свайп-карточки используют два
новых пакета — `react-native-gesture-handler` и `react-native-reanimated`
(плюс `expo-linear-gradient` для градиентов). Ровно это и сломало первую
попытку собрать APK через `eas build`: пакеты были только в коде
(импорты), но не в `package.json`/`node_modules` — Metro не мог их найти
на этапе "Bundle JavaScript". Дальше уже сама Алёна поставила их через
`npx expo install ...`, и это подняло `react-native-reanimated` до v4.5.1
— а в 4-й версии часть кода вынесена в отдельный пакет
`react-native-worklets` со своим путём к babel-плагину, из-за чего сборка
упала второй раз с той же самой формулировкой ошибки. Оба раза причину
нашли через `npx tsc --noEmit -p .` и чтение `node_modules/.../package.json`
прямо в реальной папке — `babel.config.js` я поправила сама (путь плагина
`"react-native-worklets/plugin"`), пакет `react-native-worklets` доустановила
уже Алёна. Если ещё раз всплывёт ошибка именно на шаге "Bundle JavaScript"
— первым делом гонять `npx tsc --noEmit -p .` в реальной папке, обычно это
самый быстрый способ найти нерешённый импорт.

**Статус (обновлено):** приведены к дизайну прототипа — Likes, Messages,

## Как запустить

1. Установи Node.js (18 или новее), если ещё нет.
2. В этой папке:
   ```
   npm install
   ```
   Раньше тут была ещё вторая команда (`npx expo install <длинный список
   пакетов>`) — это было нужно, потому что часть зависимостей была
   упомянута только в README, а не в самом `package.json` (моя ошибка,
   нашли и исправили при первом реальном запуске). Сейчас все пакеты уже
   прописаны в `package.json`, так что одного `npm install` достаточно.
   Если после апгрейда Expo (или добавления нового пакета) появится
   предупреждение про несовместимые версии — тогда стоит прогнать:
   ```
   npx expo install --fix
   ```
   она сама подбирает версии, которые точно совместимы с установленной
   версией Expo.

   **Новое (дизайн-переделка под настоящий прототип, см. раздел ниже) —
   ОБЯЗАТЕЛЬНО один раз выполни:**
   ```
   npx expo install react-native-gesture-handler react-native-reanimated expo-linear-gradient expo-document-picker
   ```
   Первые три пакета — для свайп-карточек на экране "Browse" (жесты +
   анимация) и градиентов (экран Welcome, подложка карточек). Четвёртый,
   `expo-document-picker`, новый — нужен для раздела "Family Room" (см.
   раздел ниже), там им выбирают файл документа (PDF или фото) для загрузки
   в общую комнату пары. Специально НЕ прописала версии этих пакетов в
   `package.json` сама — я не могу отсюда проверить, какие версии точно
   совместимы с установленной у тебя версией Expo SDK, а `expo install`
   умеет это сама и пропишет правильные версии автоматически. Все четыре —
   стандартные модули из набора Expo Go (как `expo-image-picker` и т.п.),
   НЕ такие как LiveKit/WebRTC — то есть в отличие от звонков (см. ниже) это
   должно заработать прямо в обычном Expo Go, без отдельной сборки
   dev-client.
3. Скопируй `.env.example` в `.env` и укажи адрес бэкенда:
   - если бэкенд крутится у программиста локально и телефон в той же wifi
     сети — IP компьютера в этой сети (не `localhost`!), например
     `http://192.168.1.23:8000`
   - если бэкенд уже где-то развёрнут — **программист подтвердил настоящий

## Как собрать APK

Expo Go (шаги выше) — это способ быстро посмотреть на приложение, но это
не тот файл, который можно кому-то отправить или поставить на телефон
напрямую. Для этого нужен настоящий сборочный `.apk`. Есть два пути:

**Вариант 1 — EAS Build (проще, рекомендую).** Это облачная сборка от
самой Expo — компиляция происходит не на твоём компьютере, а на серверах
Expo, поэтому не нужен ни Android Studio, ни настроенный Android SDK.
Нужен только бесплатный аккаунт на expo.dev (есть бесплатный лимит сборок
в месяц). Шаги (запускать в обычном Terminal, в папке `lbp/mobile`):
```
npm install -g eas-cli
eas login
eas build:configure
eas build --platform android --profile preview
```
`eas login` и создание аккаунта на expo.dev — это единственный шаг, который
должна сделать именно ты сама: я не могу и не должна вводить твой email,
пароль или создавать аккаунт за тебя (это касается вообще любого пароля,
не только этого). Всё остальное — просто команды, их можно копировать как
есть. После `eas build:configure` в `app.json` появится `extra.eas.projectId`
— это нормально, значит команда сработала. Сама сборка идёт 10-20 минут,
в конце `eas build` даст ссылку на страницу expo.dev, откуда `.apk` можно
скачать на любое Android-устройство или разослать напрямую (без Google Play).

**Вариант 2 — сборка локально через Android Studio/Gradle.** Тяжелее в
настройке (нужен установленный Android SDK, принятые лицензии, Java) —
имеет смысл, только если по каким-то причинам нельзя использовать
облачную сборку. Если Android Studio у тебя уже стоит — скажи, распишу
эти шаги отдельно.

**Про iOS/TestFlight** — то же самое EAS умеет и для iOS
(`eas build --platform ios`), но там обязательно нужен платный Apple
Developer аккаунт (99$/год) — это описано в разделе выше, здесь тот же
принцип: сборка облачная, вход в твой Apple ID делаешь ты сама.

На сегодня из крупного не хватает по сути только реальной сборки под звонки
(см. "Про звонки" выше) — всё остальное, что есть в бэкенде, в приложении
уже отражено и переведено на три языка. Структура (`src/api/` для обращений
к серверу, `src/screens/` для экранов, `src/navigation/` для переходов,
`src/i18n/` для переводов) заложена так, чтобы было легко добавлять новое
дальше.

### Обновление: сборка прошла, но приложение падало при запуске — заменил expo-av на expo-video

После первой сборки с видео Алёна сообщила, что приложение собралось, но
**падает сразу при запуске** — ещё до входа в аккаунт, то есть на самом
первом экране (Welcome), единственном месте, где появился новый нативный
код в этой сборке. `expo-av` (библиотека для видео, которую я поставил
первой) официально помечена Expo как устаревшая примерно с SDK 52 в пользу
`expo-video`/`expo-audio`, и известна крашами именно на новой архитектуре
(New Architecture) в свежих SDK — а его нативный модуль подключается к
проекту просто по факту наличия в зависимостях, независимо от того,
показывает ли экран `<Video>` или нет. Не имея краш-лога с телефона, чтобы
не гадать вслепую с устаревшей библиотекой, переписал `WelcomeScreen.tsx`
на `expo-video` — актуальную, поддерживаемую замену, которую сама Expo
рекомендует именно для зацикленного беззвучного фонового видео.

**Перед следующей сборкой, в реальном терминале:**

```
cd путь/до/lbp/mobile
npm uninstall expo-av
npx expo install expo-video
eas build --platform android --profile preview
```

Важно удалить именно через `npm uninstall`, а не просто убрать импорт из
кода — иначе нативный модуль `expo-av` останется подключён к проекту и,
если крашилось из-за него, ничего не изменится. Дальше как обычно:
дождаться "Build finished", на вопрос про эмулятор — **n**, установить по
ссылке/QR на телефоне.

**Если приложение всё равно упадёт на этой сборке** — это будет значить,
что причина не в expo-av/видео, и дальше без краш-лога с телефона мне будет
сложно продолжать гадать. В этом случае, если возможно, пришли: скриншот
диалога Android "Приложение остановлено" (если он появляется), либо, если
телефон можно подключить к компьютеру с установленным `adb`, вывод команды
`adb logcat *:E` сразу после краша — там будет конкретная строчка с
причиной (обычно `FATAL EXCEPTION`).

Пока `npx expo install expo-video` не выполнен, `npx tsc --noEmit -p .`
будет показывать две ожидаемые ошибки в `WelcomeScreen.tsx` — "Cannot find
module 'expo-video'" и связанную с ней ошибку типа параметра. Обе исчезнут
сразу после установки.
